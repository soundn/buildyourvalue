## Key Question 1: Cloudflare Email in 2026: what exists (Email Routing, Email Workers, Email Sending / Email Service), status, limits, pricing, deliverability tooling, and whether it allows digest-style bulk

### Takeaway
Cloudflare Email Service = Email Routing (inbound forwarding, GA for years) + Email Workers (inbound processing) + **Email Sending** (outbound), the last announced in private beta on 25 Sep 2025 and still labelled beta in the Oct 2026 docs, priced at 3,000 emails/month included on Workers Paid ($5/mo) then $0.35 per 1,000. It is positioned for transactional mail from Workers, has unpublished "conservative" daily quotas that grow with reputation, a 50-recipient cap per message, no dedicated-IP option found, and no documented bounce/complaint webhooks (dashboard + automatic suppression only). It is not a viable digest platform for this project today.

### Cited Findings
- Announcement: Cloudflare blog post dated 25 Sep 2025 announces "Email Sending, which lets developers send transactional emails from Workers... Email Sending joins and expands our popular Email Routing product, and together they form the new Cloudflare Email Service." Announced as a **private beta**. [snippet] — [Cloudflare blog: Announcing Cloudflare Email Service's private beta](https://blog.cloudflare.com/email-service/); covered by [InfoQ, Oct 2025](https://www.infoq.com/news/2025/10/cloudflare-email-service)
- Features claimed at announcement: send via a Workers Email binding in `wrangler.jsonc` with no API keys ("no risk of leaked credentials"), REST API and SMTP also supported, React Email compatible, auto-configures SPF/DKIM/DMARC, inbound mail can be processed in Workers, attachments to R2, tasks to Queues. [snippet] — [Cloudflare blog](https://blog.cloudflare.com/email-service/)
- Status as of Oct 2026 docs: "Cloudflare Email Service is currently in beta. Features and APIs may change before general availability." Sending to arbitrary recipients requires the Workers Paid plan. [snippet] — [developers.cloudflare.com/email-service](https://developers.cloudflare.com/email-service/index.md)
- Third-party trackers disagree on beta dates: one says public beta since April 2026, another says private beta since 25 Sep 2025 and still beta. Neither says GA. [snippet] — [whichdevtool.com](https://whichdevtool.com/tools/cloudflare-email-service/); [bavimail.com](https://bavimail.com/compare/cloudflare-email)
- Pricing (vendor docs excerpt): included quota is 3,000 emails per account per month; sends to verified destination addresses are free and do not count toward quota; hard-bounced messages count toward quota; requests rejected at the API boundary (including suppressed sends) do not. [snippet] — [Cloudflare Email Service docs: Pricing](https://developers.cloudflare.com/email-service/platform/pricing/)
- Pricing (third-party restating Cloudflare): Workers Free $0 but can only send to verified addresses; Workers Paid $5/mo minimum with 3,000 outbound emails included, then **$0.35 per 1,000**. [snippet] — [bavimail.com](https://bavimail.com/compare/cloudflare-email); [whichdevtool.com](https://whichdevtool.com/tools/cloudflare-email-service/)
- Limits (vendor docs excerpt): 50 recipients per email combined across to/cc/bcc; 5 MiB message size including attachments (25 MiB to verified destinations only); subject 998 chars; custom headers 16 KB combined; SMTP 50 RCPT TO per session; daily and content quotas are account-wide and shared across REST API, Workers binding and SMTP; error codes `E_DAILY_LIMIT_EXCEEDED` and `E_RATE_LIMIT_EXCEEDED`. [snippet] — [Cloudflare Email Service docs: Limits](https://developers.cloudflare.com/email-service/platform/limits/); [SMTP docs](https://developers.cloudflare.com/email-service/api/send-emails/smtp/)
- Daily quota: "New accounts start with a conservative daily quota and scale up over time based on your sending behavior, deliverability rates, and account standing." Exact numbers not published; one community thread reports a 200/day quota and a Cloudflare developer saying limits are tight "to prevent abuse and while reputation builds for sending IP". [snippet] — [Cloudflare Email Service docs: Limits](https://developers.cloudflare.com/email-service/platform/limits/); [Cloudflare Developers Discord via answeroverflow](https://www.answeroverflow.com/m/1533088772433121313)
- Suppression behaviour (vendor docs excerpt): hard bounces are never retried; mailbox/domain-not-found create a suppression with no expiry; other hard bounces suppressed 7 days; soft bounces retried with backoff and create a 24-hour suppression by default. Sep 2026 changelog: bounce and complaint suppressions now created at sending-domain level. [snippet] — [Suppression lists docs](https://developers.cloudflare.com/email-service/concepts/suppressions/); [Changelog](https://developers.cloudflare.com/email-service/platform/changelog/)
- DKIM: Email Sending and Email Routing use separate DKIM selectors; the Email Sending key is at `cf-bounce._domainkey.<domain>`. [snippet] — [Deliverability docs](https://developers.cloudflare.com/email-service/concepts/deliverability/)
- Before onboarding a sending domain you can only send to verified destination addresses; after onboarding you can send to any recipient. [snippet] — [Flavio Copes tutorial](https://flaviocopes.com/cloudflare-email-service/)
- Visibility: delivery results, bounces and suppressions are visible in the Email Service dashboard; no webhook mechanism surfaced in any search result. [snippet] — [Flavio Copes tutorial](https://flaviocopes.com/cloudflare-email-service/); [Postmaster docs](https://developers.cloudflare.com/email-service/reference/postmaster/)
- Email Routing (inbound) remains a separate, free forwarding product; Email Workers process inbound messages. The "send email from Workers" docs under email-routing predate Email Sending and only allowed replies/sends to verified addresses. [snippet] — [developers.cloudflare.com/email-routing/send-email](https://developers.cloudflare.com/email-routing/send-email/)

### Inferences
- Even if the 3x-weekly digest counted as "transactional" (it is user-requested but is marketing-shaped under Gmail/Yahoo rules), the unpublished daily quota that "scales with account standing" makes planning a 300k-per-day send impossible; there is no public path to request a 10M/day quota.
- With no dedicated IPs, no bounce/complaint webhooks, and no templating beyond "bring your own HTML", Cloudflare Email Sending is at the feature level of SES circa 2012 for an outbound bulk use case. It is sensible only for low-volume transactional mail from a Worker (OTP fallback, receipts), and only once it is GA.
- The $0.35/1,000 list price is 3.5x SES's $0.10/1,000 and roughly on par with Resend's high-volume marginal rate, so there is no cost reason to wait for it.

### Gaps
- No source found on: dedicated IP availability, template support, webhooks (vs dashboard only), explicit acceptable-use wording on marketing/newsletter sends, DMARC report handling, or a GA date. The Cloudflare limits and pricing pages could not be fetched directly; the daily-quota numbers come from one forum post.

## Key Question 2: Resend at scale: plans, overage, dedicated IPs, daily limits, Broadcasts/Audiences, webhooks, regions, rate limits, idempotency, batch API, incidents

### Takeaway
Resend's public ladder is Free (3,000/mo, 100/day), Pro $20 for 50,000, Scale $90 for 100,000 stepping up to a top public tier around 2.5M/month, then quote-based Enterprise for 3M+/month; overage is about $0.90 per 1,000 at the low Scale tiers falling to about $0.46 per 1,000 at 2.5M (third-party figures). Dedicated IPs are $30/month each (Scale plan, >3,000 emails/day) with automatic warm-up. The project crosses into Enterprise territory at roughly 500k to 1M registered users, and Resend had a 3.5-hour sending-delay incident in Feb 2026 and several shorter ones in 2026.

### Cited Findings
- Plans (Resend pricing page excerpt): Pro $20/month for 50,000 emails; Scale starts at $90/month for 100,000 emails; daily limit 100 on Free, "No limit" on Pro, Scale, Enterprise. [snippet] — [resend.com/pricing](https://resend.com/pricing); [resend.com/pricing.md](https://resend.com/pricing.md)
- Dedicated IP (Resend pricing page excerpt): "Dedicated IPs — $30 / mo: Available on the Scale plan to customers exceeding 3,000 emails sent per day. The add-on also includes automatic warmup, monitoring, and autoscaling." [snippet] — [resend.com/pricing](https://resend.com/pricing); a 2025 guide instead said the threshold was 500/day [userjot.com](https://userjot.com/blog/resend-pricing-in-2025), and a May 2026 explainer placed dedicated IPs on a "Pro 100k $90" tier [automationatlas.io](https://automationatlas.io/answers/resend-pricing-explained-2026/) — treat the vendor page as current.
- Enterprise: quote-based, aimed at teams sending 3M+ emails per month; includes SOC 2, dedicated IPs, SLAs. [snippet] — [wpmailsmtp.com Resend review 2026](https://wpmailsmtp.com/resend-review/); [sendfox.com](https://sendfox.com/compare/resend-pricing)
- Overage (third-party, conflicting): most sources put Pro overage at $0.90 per 1,000; one says $0.80 per 1,000; Scale overage listed as $0.90/1,000 at the 100k tier, $0.80 at 200k, $0.46 at 2.5M. [snippet] — [automationatlas.io](https://automationatlas.io/answers/resend-pricing-explained-2026/); [coldmailer.ai](https://coldmailer.ai/resend-pricing); [smtpedia.com](https://smtpedia.com/platforms/resend/pricing/); [usecarly.com](https://www.usecarly.com/blog/resend-pricing/)
- Rate limit (Resend docs excerpt): "All accounts start with a rate limit of 10 requests per second. If you have specific requirements, contact support to request a rate increase." Enforced per second with no burst allowance; shared across all API keys in a team. [snippet] — [Resend docs: account quotas and limits](https://resend.com/docs/knowledge-base/account-quotas-and-limits)
- Broadcasts/Audiences: marketing plans are billed on stored contacts; broadcasts to those contacts are not metered by send volume; free tier covers 1,000 contacts; paid Marketing plans start at $40/mo for 5,000 contacts (Resend blog) and a third-party table runs up to $650/mo for 150,000 contacts. [snippet] — [Resend blog: manage subscribers with Audiences](https://resend.com/blog/manage-subscribers-using-resend-audiences); [flexprice.io](https://flexprice.io/blog/detailed-resend-pricing-guide)
- Batch sending listed as included on every plan. [snippet] — [smtpedia.com](https://smtpedia.com/platforms/resend/pricing/)
- A community GitHub issue notes broadcasts have no idempotency key (not official). [snippet] — [GitHub issue totalolage/deskohub-site #584](https://github.com/totalolage/deskohub-site/issues/584)
- Incidents 2026: Resend's own incident report for 15 Feb 2026 describes email sending delays and dashboard errors from database connection exhaustion lasting 3h31m; no emails lost but most delayed ~2 hours on average; fix was smaller connection pools and per-role connection limits. [snippet] — [Resend incident report mirrored on plushcap](https://www.plushcap.com/content/resend/blog/resend-incident-report-for-february-15-2026)
- Further 2026 incidents from third-party trackers: 10 Apr 2026 major outage with 404s on SMTP and API sends; 24 Apr 2026 event-update latency for 2.9h; 17 Jun 2026 Email Events affected 38m; 10 Jul 2026 increased API latency. IsDown counts 81 Resend outages since Feb 2024. [snippet] — [isdown.app Resend outage history](https://isdown.app/status/resend/outage-history); [pingoru.io Resend](https://pingoru.io/providers/resend/outage-history)

### Inferences
- At 10 req/s and batch sends, a Node job runner can push roughly 1,000 emails/s if each batch request carries 100 emails (batch size unverified, see Gaps), i.e. 3M digests in under an hour; if batch is unavailable or small, 10 req/s is a hard ceiling of 36,000 emails/hour and the 3M-digest day at 10M users would take 83 hours. The rate limit must be raised with support before the 100k-user tier.
- Resend's contact-priced Broadcasts product does not fit a per-user personalised digest (each digest is a distinct body), so digests would run through the transactional API at per-email pricing, not through Audiences.
- Shared-pool incidents (sending delays of ~2h) matter less for a thrice-weekly digest than for OTPs; the project should route OTP/receipts on a separate stream or provider from day one.

### Gaps
- Could not verify from vendor pages: exact Scale tier prices above 100k (the 2.5M tier price), batch API limit (training knowledge says 100 emails per batch request and an `Idempotency-Key` header exists; unverified here), EU/US/other region options (training knowledge: us-east-1, eu-west-1, sa-east-1, ap-northeast-1; unverified), webhook event list, Enterprise per-1,000 pricing, and any public report on Resend shared-IP reputation. No source on Resend deliverability to Nigerian recipients.

## Key Question 3: Amazon SES: pricing, dedicated IPs (standard and managed), Virtual Deliverability Manager, quotas and warm-up, regions (eu-west-2, af-south-1), reputation dashboard, suppression lists, templates/React Email

### Takeaway
SES is $0.10 per 1,000 outbound emails with no plan ceiling; dedicated IPs are $24.95/month each (self-managed warm-up) or Managed Dedicated IPs at $15/month/account plus $0.08 per 1,000 falling to $0.02 per 1,000 above 50M/month with automatic warm-up and pool scaling; Virtual Deliverability Manager adds $0.07 per 1,000 (falling to $0.02 above 100M). af-south-1 (Cape Town) is a supported SES region with its own quotas. At 59M emails/month the all-in SES bill is on the order of $9k to $12k, roughly a third to a half of any SaaS alternative's list price.

### Cited Findings
- Outbound price: $0.10 per 1,000 emails (consistent across the AWS page excerpt and every secondary source). [snippet] — [aws.amazon.com/ses/pricing](https://aws.amazon.com/ses/pricing/); [mailblast.io](https://www.mailblast.io/blog/ses/amazon-ses-pricing); [sendops.dev](https://sendops.dev/amazon-ses-pricing/)
- Dedicated IPs (Standard): "$24.95 / month / IP"; "You get a dedicated IP address and manage the warm-up schedule yourself." [snippet] — [aws.amazon.com/ses/pricing](https://aws.amazon.com/ses/pricing/)
- Dedicated IPs (Managed): $15 / month / account plus per-email fee of $0.08 per 1,000 (0–10M), $0.04 per 1,000 (10–50M), $0.02 per 1,000 (50–100M); "AWS handles the warm-up automatically and scales the IP pool as your volume grows." [snippet] — [aws.amazon.com/ses/pricing](https://aws.amazon.com/ses/pricing/)
- Virtual Deliverability Manager: per-email fee $0.07/1,000 (0–10M emails per month), $0.05/1,000 (10–100M), $0.02/1,000 (>100M); queries $0.0005/1,000 with first 5,000 queries/month free. A separate "VDM Global deliverability" tier is $1,250/month per region per account, including 5 domains, 12 IPs and 25 seed-list tests per month, with overages $25/domain, $12.50/IP, $10/seed list test. [snippet] — [aws.amazon.com/ses/pricing](https://aws.amazon.com/ses/pricing/); contradicted by [leadsnipper.com](https://leadsnipper.com/blog/amazon-ses-pricing-2026) which claims VDM is $1.00 per 1,000 (almost certainly an error).
- SES has endpoints in Africa (Cape Town) af-south-1: `email.af-south-1.amazonaws.com` and `email.af-south-1.api.aws`. Quotas are tracked separately per region. [snippet] — [AWS General Reference: SES endpoints and quotas](https://docs.aws.amazon.com/general/latest/gr/ses.html)
- Sandbox limits are 200 emails per 24 hours and 1 per second; out of sandbox "the limit varies based on your specific use case"; quota is on a rolling 24-hour window; `GetSendQuota` returns the current 24-hour quota and max send rate. [snippet] — [Managing your Amazon SES sending limits](https://docs.aws.amazon.com/ses/latest/dg/manage-sending-quotas.html); [SES service quotas](https://docs.aws.amazon.com/ses/latest/DeveloperGuide/quotas.html)
- Automatic warm-up for dedicated IPs exists; AWS notes the old 50,000-per-day cap during warm-up "has since been removed". [snippet] — [AWS Messaging Blog: SES can now automatically warm up your dedicated IPs](https://aws.amazon.com/blogs/messaging-and-targeting/amazon-ses-can-now-automatic-warm-up-your-dedicated-ip-addresses/)
- Bulk templated sending: `SendBulkTemplatedEmail` caps at 50 destinations per call across To/CC/BCC; a single invalid address rejects the whole call; up to 10,000 templates per account, each up to 500 KB including text and HTML parts; a 2026 tutorial sends in batches of 50 with `DefaultTemplateData` fallback and per-destination status checks. [snippet] — [SES API Reference: SendBulkTemplatedEmail](https://docs.aws.amazon.com/goto/WebAPI/email/SendBulkTemplatedEmail); [AWS blog: introducing email templates and bulk sending](https://aws.amazon.com/blogs/messaging-and-targeting/introducing-email-templates-and-bulk-sending/); [oneuptime.com, Feb 2026](https://oneuptime.com/blog/post/2026-02-12-send-bulk-emails-with-amazon-ses/markdown)
- Free tier: secondary sources cite 3,000 emails/month free for the first 12 months (not confirmed from the AWS excerpt). [snippet] — [emercury.net](https://www.emercury.net/blog/email-marketing-tips/amazon-ses-pricing/)

### Inferences
- Managed Dedicated IPs are the right SES option for this team: the per-email surcharge at 59M/month is about $2,775 versus roughly $200 for 8 self-managed IPs, but it removes warm-up scheduling and pool sizing, which a two-person team should not hand-roll. Switch to Standard IPs only once volume is stable and someone owns deliverability.
- For a per-user personalised digest, SES templates (Handlebars-style merge fields, 500 KB) can carry a fixed layout with per-recipient job lists injected as template data, so one `SendBulkTemplatedEmail` call can deliver 50 distinct digests; this is the cheapest API path (one call per 50 users). Alternatively render with React Email in Node and call `SendEmail` per user, which is simpler but 50x more API calls.
- af-south-1 is useful for data-residency optics and lower API latency from a Lagos-adjacent runner, but IP reputation is per IP, not per region, so it does not by itself improve Gmail/Yahoo placement; Gmail's filtering is global.

### Gaps
- Could not fetch the SES pricing page; the Managed Dedicated IP fee above 100M/month and whether the tiers are marginal or whole-volume are not confirmed in the excerpts (the model below treats them as marginal). No source found on af-south-1 default out-of-sandbox quota or on SES VDM advisor features (reputation dashboard, suppression list behaviour) in this session; these are standard SES features per training knowledge but unverified here.

## Key Question 5: Deliverability at scale: Gmail/Yahoo bulk-sender rules, warm-up schedules, IP sizing at 10M/50M users, Postmaster Tools v2, seed testing, shared-pool risk, Nigeria-specific evidence

### Takeaway
Gmail and Yahoo treat anyone sending about 5,000+ messages/day as a bulk sender: SPF and DKIM both required, DMARC (at least p=none) aligned with the From domain, RFC 8058 one-click unsubscribe honoured within 48 hours on marketing-style mail, user-reported spam under 0.3% (0.1% as the practical target), and since late 2025 Gmail rejects or rate-limits non-compliant traffic. A well-warmed dedicated IP can carry 1–2M emails/day (one practitioner reports 2.5M/day from 4 IPs), so the project needs roughly 2–4 IPs at 10M users and 8–15 at 50M, warmed over 4–8 weeks; Postmaster Tools v2 now gives a pass/fail compliance dashboard and retires the IP/domain reputation charts. No study of Gmail/Yahoo deliverability specifically to Nigerian recipients was found.

### Cited Findings
- Gmail: mitigations (via Postmaster Tools) become unavailable when user-reported spam exceeds 0.3%; eligibility returns after 7 consecutive days below that. [snippet] — [Google Workspace Admin Help: email sender guidelines FAQ](https://support.google.com/a/answer/14229414)
- Gmail enforcement, Nov 2025: Gmail now rejects or rate-limits non-compliant bulk traffic; the grace period has ended; unsubscribe must be honoured within 48 hours and RFC 8058 headers supported. [snippet] — [Red Sift: Gmail's enforcement ramps up](https://redsift.com/resources/blog/gmails-enforcement-ramps-up-what-bulk-senders-need-to-know)
- Threshold: about 5,000 or more messages a day to personal Gmail accounts, with subdomains counted under the same primary domain; one-click unsubscribe applies to marketing/promotional mail, not transactional (password resets); a body link alone does not satisfy it because the `List-Unsubscribe` header powers Gmail's native button. ### Inferences
- Digest-day peaks under the 30%-MAU assumption: 300 (1k users), 30k (100k), 300k (1M), 3M (10M), 15M (50M). Ceiling if every registered user received 3/week: 1M, 10M, 50M per digest day. IP count at 1–2M/day per IP plus one spare: 1M users = 1–2 IPs (optional); 10M users = 3–4 IPs (6–11 at ceiling); 50M users = 9–16 IPs (26–51 at ceiling). SES Managed Dedicated IPs or Resend's "autoscaling" dedicated IPs remove the need to size this by hand.
- The 3x-weekly cadence is an advantage for warm-up (predictable, repeated volume) and a disadvantage for IP count (all volume lands on three days; sending windows should be spread over 6–8 hours, and the 30% MAU can be staggered by cohort).
- The job digest is "marketing-shaped" under Gmail's rules even though users asked for it: it must carry `List-Unsubscribe` + `List-Unsubscribe-Post` (RFC 8058), a visible unsubscribe link, and be on a separate subdomain/stream from OTP and receipts so a spam-rate spike cannot block login mail. This matches the email-template skill's existing rules in this repo.
- Shared pools at Resend/Postmark/Mailgun are fine until ~100k users (30k/digest day, under the 100k/month dedicated-IP guidance); past ~500k users the project is a top-tier sender on any shared pool and its own reputation is hostage to neighbours, so dedicated IPs should be warmed before the 1M-user mark.
- No evidence was found that Gmail or Yahoo treat Nigerian recipients differently; the only documented bias is an Outlook content filter on the word "Nigeria". Content (job titles, salary in naira, "apply free") is still worth seed-testing because scam-adjacent vocabulary ("earn", "no fee", "urgent hiring") overlaps the project's domain.

## Key Question 7: Architecture notes: Worker vs Node job runner, template rendering cost, personalisation at 100M+/month, suppression and unsubscribe handling, multi-provider failover

### Takeaway
The sensible shape for this repo is a Node job runner (the existing `api` service or a pg_cron/pgmq-driven worker) that renders per-user digests and calls the provider behind a small internal `EmailProvider` interface, with SES `SendBulkTemplatedEmail` (50 personalised recipients per call) or Resend batch as the hot path, suppression stored in Postgres and mirrored from provider bounce/complaint webhooks, and a second provider configured as a circuit-breaker fallback for transactional streams only.

### Cited Findings
- Cloudflare Email Sending is bound to Workers via an Email binding with no API keys, and also exposes REST and SMTP; quotas are account-wide across binding, REST and SMTP. [snippet] — [Cloudflare blog](https://blog.cloudflare.com/email-service/); [Workers API docs](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/)
- SES bulk templated send: 50 destinations per call, per-destination replacement data with `DefaultTemplateData` fallback, per-destination status in the response; account max send rate can limit destinations accepted per call. [snippet] — [SES API Reference](https://docs.aws.amazon.com/goto/WebAPI/email/SendBulkTemplatedEmail); [oneuptime.com tutorial](https://oneuptime.com/blog/post/2026-02-12-send-bulk-emails-with-amazon-ses/markdown)
- Resend API: 10 requests/second per team, no burst, raiseable by support. [snippet] — [Resend docs](https://resend.com/docs/knowledge-base/account-quotas-and-limits)
- Postmark pauses accounts that send promotional mail on a transactional stream; streams use different IPs and From domains automatically. [snippet] — [Postmark](https://postmarkapp.com/blog/send-promotional-email-with-postmark-message-streams)
- Cloudflare suppression lists are automatic (hard bounce permanent/7-day, soft 24h, per sending domain since Sep 2026) with dashboard visibility. [snippet] — [Cloudflare suppression docs](https://developers.cloudflare.com/email-service/concepts/suppressions/)
- Gmail requires RFC 8058 one-click unsubscribe honoured within 48 hours on marketing-style mail; the header, not just a body link, drives Gmail's unsubscribe button. [snippet] — [Red Sift](https://redsift.com/resources/blog/gmails-enforcement-ramps-up-what-bulk-senders-need-to-know); [suped.com](https://www.suped.com/email-deliverability/answers/how-to-comply-with-gmails-new-sending-rules-for-bulk-email-sender)
- Multi-provider failover libraries in Node are thin: `@upyo/pool` (load balancing and failover across transports implementing one interface), `emailer-js` (SendGrid/Mailgun/SES keys), Superface OneSDK tutorial (SendGrid primary, Postmark secondary, circuit-breaker policy); ChainMail is the mature equivalent but in Ruby. [snippet] — [jsr.io @upyo/pool](https://jsr.io/@upyo/pool@0.5.1/doc/~/PoolTransport); [npm emailer-js](https://www.npmjs.com/package/emailer-js); [dev.to Superface](https://dev.to/superface/don-t-get-burned-by-email-6c4); [ChainMail gem](https://rubygems.org/gems/chain_mail)

### Inferences
- Worker vs Node: Cloudflare's binding-only, quota-gated beta is the only reason to send from a Worker; since this repo's API is Hono on Node with Supabase, a Node job runner (pgmq queue of `digest_jobs`, workers pulling batches of 50 users) is the natural fit and works with every provider over HTTPS.
- Rendering cost: at 59M digests/month, rendering a React Email component per user in Node (typically single-digit milliseconds each) is on the order of a few CPU-hours per digest day, negligible next to API latency; the real constraint is API call count, so prefer provider-side templates (SES 50-per-call) or batch endpoints (Resend batch) over one HTTPS call per user. Keep the digest body under ~100 KB so Gmail does not clip it (this is the repo's existing email-template rule).
- Suppression and unsubscribe should be owned in Postgres (a `email_suppressions` table keyed by address and stream, written from provider webhooks and from the one-click endpoint) rather than relying on each provider's list, because a provider migration would otherwise drop suppressions and immediately spike the spam rate; the `new-migration` skill applies.
- Failover: keep it for the transactional stream only (OTP fallback, receipts), where a 2-hour delay is unacceptable; a digest can simply be re-queued. Running digests on two providers simultaneously splits reputation and doubles warm-up work.
- Recommendation on provider moves: start on Resend Pro ($20) for speed of integration and webhooks; write the provider interface on day one; open an SES account in eu-west-2 or af-south-1 at roughly 100k users and begin warming Managed Dedicated IPs for the digest subdomain; cut the digest stream to SES before ~500k users (where Resend becomes Enterprise-only and 3–5x the cost); keep Resend (or Postmark) for transactional mail as the second provider. Revisit Cloudflare Email Sending only when it is GA with published quotas, webhooks and dedicated IPs.

### Gaps
- No engineering case study at 100M+/month was retrieved; React Email per-render cost figures are from general knowledge, not a source. Resend webhook event list and batch limits unverified. No source compares bounce-webhook latency across providers.
