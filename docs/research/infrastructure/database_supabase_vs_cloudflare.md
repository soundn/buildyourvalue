## Key question 1: Supabase at scale in 2026 (plans, compute, replicas, pooling, storage, egress, Auth MAU, pgvector, backups, regions, branching, Free pause)

### Takeaway
Supabase is still plain AWS-hosted Postgres with published, linear add-on pricing up to a 16XL instance (64 vCPU / 256 GB RAM, ~$3,730/month, 500 direct connections, 12,000 pooler clients) and "Contact Us" above that; Auth is metered at $0.00325 per MAU beyond 100,000 on Pro/Team, which is cheap per user but becomes the single largest line item (≈$48k/month) at 15M MAU. Supabase's own pgvector benchmarks stop at 1M vectors per database and its scaling guidance is to split vector collections into separate "pod" projects; there is no African region (London eu-west-2 is the nearest listed), Free projects pause after 7 days of inactivity, and branching is $0.01344 per branch-hour.

### Inferences
- A single Supabase project tops out at 16XL (256 GB RAM). Using Supabase's own 1M × 1536-dim figure of ~32–40 GB RAM in use, 50M profile embeddings at 1,024 dims (raw float32 ≈ 205 GB; HNSW index ≈ 1.2–2× raw ≈ 250–410 GB; see KQ3 arithmetic) cannot be served from one instance. Following Supabase's "pods" guidance that means roughly 3–8 vector projects (or halfvec/binary quantisation to halve or quarter the footprint), each with its own compute bill, and application-side fan-out and merge.
- Operational Postgres data (20 KB profile + metadata ≈ 35 KB per user, my assumption) is ~1.7 TB at 50M users, inside the 16XL "10 TB recommended" envelope but far beyond anything Supabase has publicly documented a customer running on one project; 10M users (~350 GB) fits a 4XL by Supabase's recommended max-DB-size table.
- Auth at $0.00325/MAU is roughly six times cheaper than Clerk's $0.02 (KQ2) and is the only consumer-grade auth bundled into a database plan at list price; it still reaches ≈$48k/month at 15M MAU, which is Enterprise-negotiation territory.
- Pooler capacity (12,000 clients at 16XL) is adequate for a Hono API behind an application-side pool, but each read replica only helps PostgREST GETs and direct SQL; Auth always hits the primary.

### Gaps
- Supabase does not publish pricing for >16XL, Enterprise MAU rates, or Enterprise plan fees; those require sales quotes.
- No Supabase (or independent) benchmark exists for pgvector at 10M–50M vectors on Supabase compute; HNSW build times at that scale are not published anywhere I could find.
- Read-replica count limits (maximum replicas per project) are not stated in the fetched docs.
- Egress pricing per region (e.g. whether London costs the same as US) is not broken out.
- Multigres pricing/availability on the hosted platform is unannounced.

## Key question 2: Cloudflare data products in 2026 (D1, Hyperdrive, R2, Durable Objects, KV, Vectorize, Queues, Access) and consumer auth

### Takeaway
Cloudflare's own primitives are cheap and egress-free but each has a hard ceiling that forces sharding at this scale: D1 is capped at 10 GB per database (1 TB per account by default), Durable Objects at 10 GB per object, Vectorize at 20M vectors and 1,536 dimensions per index with no pgvector-style SQL joins; Hyperdrive is a free (with the $5 Workers Paid plan) pooler/cache to an external Postgres with ~100 origin connections per config. Cloudflare Access is workforce Zero Trust (50 users free, then $7 per user per month) and Cloudflare sells no consumer identity product; consumer auth must come from Supabase Auth, Clerk, Auth0, Stytch, Better Auth or Neon's Managed Better Auth.

### Inferences
- With ~35 KB of relational data per user (my assumption), a 10 GB D1 database holds ~285,000 users; 10M users need ~35 databases and 50M users ~175 databases plus a raised 1 TB account cap. Cross-shard queries (admin analytics, employer search) would have to be done in Workers or in a separate analytical store.
- A per-user Durable Object (one SQLite DO per user, 10 GB cap each) is a natural fit for profile + CV metadata and is the cheapest Cloudflare storage ($0.20/GB-month vs D1's $0.75), but it has no cross-user query capability at all; any "find candidates for this job" query needs Vectorize or an external Postgres.
- Vectorize can serve the forward match (query 220k job vectors with each user's embedding) cheaply at any user scale; a reverse index of all users would need 3 indexes at 50M (20M cap) with client-side merge, and 1,024-dim embeddings fit the 1,536 cap while 1,536-dim ones are the maximum.
- There is no Cloudflare consumer identity product; the realistic pairings are (i) Supabase Auth over Hyperdrive, (ii) Neon Managed Better Auth (included to 1M MAU), (iii) self-hosted Better Auth in Workers against Postgres/D1, or (iv) Clerk/Auth0/Stytch, which are 6–30× the per-MAU price of Supabase Auth at list.

### Inferences (arithmetic, mine)
- Raw float32 storage for 1,024-dim embeddings = 4 KB per vector: 1M → 4 GB, 10M → 41 GB, 50M → 205 GB. With the 1.2–2× HNSW index multiplier: 10M → 49–82 GB RAM for the index alone (fits a Supabase 8XL/12XL, a Neon 16–24 CU, or a 128 GB Hetzner box); 50M → 246–410 GB (exceeds Supabase 16XL's 256 GB and Neon's 224 GB fixed max; fits only an Aurora r6g.16xlarge-class instance at ~$3.3–7.9k/month or 2–4 shards). `halfvec(1024)` halves these (50M → 102 GB raw).
- Critically, the product only needs the *forward* match (each active user's vector queried against ~220k job vectors, see KQ5 assumptions). A 220k × 1,024-dim HNSW index is < 2 GB and runs on a Medium/Large Supabase instance or 1–2 CU Neon. The 50M-profile index is only required for reverse search (employer → candidates); if that feature is deferred or served from Vectorize/quantised halfvec shards, no Postgres host needs to hold a 50M-vector HNSW graph.
- Neon's per-GB storage ($0.35) is 2.8× Supabase's gp3 disk ($0.125), but Neon bills logical data size while Supabase bills provisioned disk (which cannot shrink) and Neon has no fixed plan fee; at ≤1M users Neon is cheaper, at 10M+ the storage line reverses.

## Key question 4: Nigeria data protection fit (NDPA 2023, GAID 2025, cross-border transfer, African regions, what a Transfer Impact Assessment must say)

### Takeaway
Hosting Nigerian users' CVs on any of these providers is a cross-border transfer under the NDPA/GAID: the NDPC has published no adequacy decisions and the 2019 NDPR whitelist no longer applies, so the lawful route is an NDPC-approved Cross-Border Data Transfer Instrument (SCCs/BCRs with prior approval) or a narrow derogation such as explicit consent, documented in a transfer assessment and reported semi-annually. No provider in this comparison offers an African region except AWS (Cape Town) and Azure (South Africa North); Cloudflare's Lagos facility is an edge PoP with no storage jurisdiction for Africa, and the new National Digital Cloud Policy (Oct 2026) requires "Level 3" data (financial, health, biometric, identity) to be stored at rest in Nigeria.

- GAID 2025 "took effect on 19 September 2025" and permits transfers "only under conditions such as adequacy decisions, approved transfer instruments, or other lawful bases under Sections 41–43 of the NDP Act". - Supabase (London, eu-west-2): processor = Supabase Inc (US) with AWS UK as sub-processor; data at rest in the UK; UK has an independent regulator (ICO) and enforceable rights, satisfying Schedule 5 factors; transfer instrument = Supabase DPA plus NDPC-approved SCCs (prior approval); note that Auth tokens, logs (7–28 day retention), log drains, and any US-based sub-processors (support tooling, analytics) are additional transfers; list Storage (CV files) and backups as UK-resident; state that no African region exists and record the plan to revisit if Supabase adds one.
- Cloudflare-native: processor = Cloudflare Inc (US); D1/DO/R2 can be pinned to the "eu" jurisdiction (not UK, not Africa); Vectorize cannot be pinned anywhere (no DLS support) and Workers run globally unless Regional Services (Enterprise feature) is used; data in transit terminates TLS at the Lagos PoP under Cloudflare's control; the TIA must therefore cover a multi-country processing footprint and justify Vectorize's unknown location — materially weaker than a single-region Postgres.
- Workers + Hyperdrive + Neon/Supabase (London): same as Supabase for data at rest, plus Hyperdrive caches query results at Cloudflare edge locations worldwide (cached query responses up to 50 MB), so cached personal data transits/rests briefly outside the UK; disable caching for PII queries or document it.
- CVs with NIN/BVN or biometric data would be "Level 3" under the Cloud Policy and arguably must be stored in Nigeria at rest; a mitigation is to avoid collecting identity numbers and to treat the Cloud Policy as a trajectory indicator (not binding law yet) while planning an AWS Cape Town or Nigerian-hosted option (AFRICLOUD Lagos region exists per [tech.africa](https://tech.africa/africloud-opens-its-lagos-region-nigeria-joins-lisbon-and-johannesburg/) [snippet]).

### Gaps
- Primary GAID 2025 text (ndpc.gov.ng) was unreachable; article numbering (Art. 45 / Schedule 5) and the exact consent rule should be checked against the directive.
- No NDPC-published template or guidance for a Transfer Impact Assessment was found; the TIA content above is inferred from GAID Schedule 5 factors as summarised by law firms.
- The CBN June 2026 localisation directive is unverified.
- Whether any CBDTI (SCC template) has yet been approved by the NDPC in 2026 is unknown.

## Key question 5: Cost model at 1,000 / 100,000 / 1M / 10M / 50M registered users

### Takeaway
At list price the three routes cost about the same below 100k users (tens of dollars), diverge by an order of magnitude at 1M–10M, and at 50M users a Workers + Hyperdrive + Neon design (~$2k/month) is ~25× cheaper than Supabase (~$57k/month, 85% of which is the $0.00325/MAU Auth fee) and ~150× cheaper than Cloudflare-native + Clerk (~$300k/month, 99% of which is Clerk's $0.02/MRU). Database and object storage are never the dominant cost; identity pricing and, in naira, SMS OTP delivery are.

### Assumptions (all mine; change any one and the table shifts)
1. Monthly active users = 30% of registered users.
2. Postgres footprint ≈ 35 KB per user: 20 KB profile JSON + 4 KB embedding (1,024 × float32) + ~5 KB HNSW index share + ~6 KB other rows/indexes. Rounded: 1M users ≈ 33 GB, 10M ≈ 334 GB, 50M ≈ 1.67 TB.
3. CV files: 200 KB per user, one CV each, in object storage: 1M ≈ 191 GB, 10M ≈ 1.9 TB, 50M ≈ 9.5 TB.
4. Job listings: 300/day, retained 2 years ≈ 220,000 live embeddings at 1,024 dims (≈0.9 GB raw).
5. Matching: one run per active user per week = 4.33 runs per MAU per month, implemented as a forward query (user vector → job index). Reverse indexing of all users is costed separately.
6. Traffic: 4.33 sessions/MAU/month, 100 rows read per session, 50 rows written per MAU per month, 20 API requests per MAU per month, 3 MB egress per MAU per month (profiles + occasional CV download).
7. Supabase compute tier chosen by Supabase's "recommended max DB size": Micro ≤1k users, Medium at 100k, XL at 1M, 4XL at 10M, 16XL at 50M; PITR 7-day add-on from 100k users; Pro plan to 1M users, Team from 10M; $10 compute credit applied. No read replica included (adding one doubles compute + 1.25× disk).
8. Cloudflare-native: D1 for relational data (sharded as needed), R2 for CVs, Vectorize for the job index, Workers Paid $5, Clerk Pro ($25 + $0.02 per retained user above 50k; retained users assumed = MAU).
9. Workers + Hyperdrive + Neon: Neon Launch rates, always-on compute sized 0.25 CU / 1 CU / 2 CU / 8 CU / 16 CU across the tiers, storage $0.35/GB-month, R2 for CVs, Workers Paid; Hyperdrive $0; auth via Neon Managed Better Auth (included to 1M MAU; above that "request an increase", price unknown) — so the auth line is $0 to 1M users and **unpriced** above.
10. Compute at 10M+ on any route is a floor: no HA standby, no replicas, no staging environments, no observability spend.
11. SMS OTP priced in naira at ₦7 per message (mid-point of ₦5.62–₦8.00 per 160-char page) with two scenarios: 0.3 OTP per MAU per month (long-lived sessions) and 1.0 per MAU per month; identical across routes.

## Key question 6: Migration paths and lock-in

### Takeaway
Supabase → Neon/RDS/self-hosted is a standard `pg_dump`/`psql` move (Supabase even documents the three-dump procedure), with real friction only in the `auth` and `storage` schemas, Vault/encryption keys, custom-role passwords and Storage objects; Supabase Auth → another provider is feasible because bcrypt hashes and phone numbers sit in `auth.users` and WorkOS/PropelAuth publish import guides; D1 → Postgres is a SQLite `.sql` dump through pgloader with type-affinity, boolean and date pitfalls, and per-database (≤10 GB) exports that must be stitched together.

### Cited Findings
- Supabase documents moving a project by logical dump: `supabase db dump ... -f roles.sql --role-only`, `-f schema.sql`, `-f data.sql --use-copy --data-only` (excluding `storage.buckets_vectors` / `storage.vector_indexes`), then `psql` restore; caveats: "Backup files never contain the root key ... Vault secrets and encrypted columns restored from the old project cannot be decrypted until you copy the old key across"; "If you have modified the auth and storage schemas ... you have to restore them separately"; "Custom roles require passwords"; Storage objects must be copied bucket-by-bucket with a script; Edge Function import maps are not downloaded. — [Backup and restore (migrating within Supabase)](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) [fetched source]
- Daily backups "do not include objects you store via the Storage API"; PITR physical backups "are not available for direct download" — you need a manual `pg_dump`. — [Database Backups](https://supabase.com/docs/guides/platform/backups) [fetched source]
- Supabase Auth export: hashes are in `auth.users.encrypted_password` ("using the bcrypt algorithm"); WorkOS's sample export includes `phone` and `phone_confirmed_at`; join `auth.identities` for social logins; WorkOS imports bcrypt so "users can continue to sign in with their existing password without needing to reset it". — [WorkOS: Migrate from Supabase Auth](https://workos.com/docs/migrate/supabase) [snippet]; [PropelAuth: Migrating users from Supabase](https://docs.propelauth.com/migrations/supabase) [snippet]
- Reverse direction (into Supabase) is documented by Supabase: set `email_confirm`/`phone_confirm: true` when recreating confirmed users via the admin API. — [Migrate from Auth0 to Supabase Auth](https://supabase.com/docs/guides/auth/migrations/auth0) [snippet]
- Supabase accepts third-party JWTs from Clerk, Firebase Auth, Auth0 and AWS Cognito and bills them as Third-Party MAUs at the same $0.00325 rate — so swapping the IdP does not require leaving the database. — [Third-Party MAU](https://supabase.com/docs/guides/platform/manage-your-usage/monthly-active-users-third-party) [fetched source]
- Cloudflare Hyperdrive can front an existing Supabase database (direct connection string), so adding Workers in front of Supabase is additive, not a migration. — [Hyperdrive + Supabase](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-database-providers/supabase/) [fetched source]
- D1 export: `wrangler d1 export` produces a `.sql` file; imports limited to 5 GiB per file; raw `.sqlite3` must be converted with `sqlite3 ... .dump`. — [D1 Import and export](https://developers.cloudflare.com/d1/best-practices/import-export-data/) [fetched source]
- pgloader loads SQLite directly with schema discovery; risks: SQLite type affinity ("allowing you to store a string in an INTEGER column"), booleans stored as 0/1, dates stored as TEXT/INTEGER — "Your application code parsing string dates will break". Neon publishes a SQLite→Neon pgloader guide with CAST clauses and sequence checks. — [pgloader SQLite reference](https://pgloader.readthedocs.io/en/latest/ref/sqlite.html) [snippet]; [Neon: migrate from SQLite](https://neon.com/docs/import/migrate-sqlite) [snippet]; [render.com guide](https://render-www.onrender.com/articles/how-to-migrate-from-sqlite-to-postgresql) [snippet]
- Neon: "You cannot change the region for an existing project ... create a new Neon project in that region and migrate your database". — [Neon regions](https://neon.com/docs/introduction/regions) [fetched source]
- Cloudflare: D1/DO/R2 jurisdictions and DO locations "cannot be changed" after creation. — [D1 data location](https://developers.cloudflare.com/d1/configuration/data-location/) [fetched source]; [DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/) [fetched source]

### Inferences
- Lock-in ranking (least → most): plain Postgres on Supabase/Neon/RDS (schema + pgvector are portable; only the Supabase-specific `auth`/`storage` schemas, RLS tied to `auth.uid()`, Edge Functions and Realtime are sticky) < Supabase Auth (portable hashes, but phone-only users have no password to migrate and must re-OTP; social identities need re-linking) < Vectorize (no export format beyond list/query; re-embed or re-upsert) < Durable Objects per-user state (50M isolated SQLite files with no bulk export tool — would need a Worker to iterate every object) ≈ D1 at scale (175 databases × ≤5 GiB export files).
- The cheapest reversible first step for the current stack (Supabase Postgres + Auth, Hono API) is to keep Supabase for data and identity and put Workers + Hyperdrive in front only if edge latency to Nigeria matters; it costs nothing extra and preserves the pg_dump exit.
- Because Supabase bills third-party IdP users at the same $0.00325, moving auth to Clerk later would add Clerk's fee without removing Supabase's — a reason to keep Supabase Auth (or go fully self-hosted Better Auth) rather than mix.

### Gaps
- No documented bulk export path for Vectorize indexes or for iterating all Durable Objects in a namespace was found.
- Phone-OTP-only user migration between providers (no password hash to carry) is undocumented by any provider found; assume users re-verify on first login after a move.
- RLS policies referencing Supabase-specific functions (`auth.uid()`, `auth.jwt()`) must be rewritten for a non-Supabase host; effort depends on policy count (project-specific, not researched).

## Overall synthesis for the report writer (inferences)
- Capability: Supabase Postgres + pgvector + Auth + Storage is a complete fit today and stays plain Postgres; Cloudflare-native storage lacks SQL vector search and consumer identity and imposes 10 GB/20M-vector shards that must be managed in application code; Workers + Hyperdrive + external Postgres is additive to either Supabase or Neon.
- Limits that bite at 50M: Supabase 16XL/256 GB RAM (vector index must be sharded into pods or quantised), Supavisor 12,000 clients, no African region; D1 10 GB/db and 1 TB/account, Vectorize 20M vectors and 1,536 dims; Neon 56 CU/224 GB.
- Cost: storage is cheap everywhere (<$2.5k/month at 50M for 1.7 TB + 9.5 TB of CVs on any route); identity is the cost — Supabase Auth ≈$48k/month at 15M MAU, Clerk ≈$299k/month; Neon's bundled auth is free to 1M MAU and unpriced beyond.
- Operations for two founders: Supabase = one console, one bill, 2-minute compute resizes, 2-minute-RPO PITR for $100, but vendor-dependent above 16XL; Cloudflare-native = many small databases and indexes with scale-to-zero billing but bespoke sharding, consistency and export code; Neon = no plan fee, autoscaling with no reconnects, London region, but a second vendor for auth/SMS unless Managed Better Auth is used.
- Data protection: all three keep data outside Nigeria; a London (eu-west-2) single region with an approved CBDTI is the most defensible TIA; Vectorize and Hyperdrive caching weaken it; an AWS Cape Town or Nigerian-hosted Postgres is the only way to satisfy a strict reading of the Cloud Policy's Level 3 rule.
- Migration: everything that is Postgres moves with pg_dump; Supabase Auth hashes and phone numbers export; D1 exports as SQLite SQL and converts with pgloader; Vectorize and Durable Objects have no bulk export path.
